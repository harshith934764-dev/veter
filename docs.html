01 · Overview

What is Veter?

Veter is an independently developed programming-language project. It has its own .vtr source-file extension, language design, compiler/runtime experiments and developer tools. The project aims to develop a readable, consistent language and a practical ecosystem for building software.

Veter is an evolving project. A feature described as a design goal or proposal is not automatically available in every compiler or runtime build.

Design principles

  • Distinct language identity rather than a renamed copy of another language.
  • Readable statements and consistent grammar.
  • Predictable types, operators, control flow and error behaviour.
  • Useful diagnostics that identify the source location of errors.
  • Compatibility rules and tests before declaring stable releases.
02 · Source files

Files and project layout

Veter source examples use UTF-8 text and the .vtr extension.

hello.vtr

# A small Veter program
remember score as 95
display score

Use a text editor or a compatible Veter tool to create a source file. A file extension does not execute a program; execution requires a compatible compiler, interpreter or runtime.

03 · Syntax model

Core language concepts

The supplied Core 1.0 prototype README documents the following command family:

DOCUMENTED IN CORE 1.0 PROTOTYPE
remember score as 95
display score

choose when score >= 50
    display "passed"
else choose
    display "try again"
close choice

remember count as 1
repeat 3 rounds
    display count
    revise count as count + 1
close cycle

These examples describe the Core 1.0 prototype documented in the supplied repository. Confirm the exact executable and build you are using before relying on them in another release.

05 · Compatibility

Know which features are available

  • PROTOTYPE-DOCUMENTED Core 1.0 README lists variable storage, output, input, conditions and loops.
  • BROWSER DEMO The homepage playground implements a limited subset: make, set, say, show, strings and arithmetic.
  • PROPOSED The language specification includes future design proposals that require implementation and tests.
Do not assume a command supported by the website demo is supported by every native compiler, or vice versa.
06 · Developer workflow

Recommended workflow

  1. Choose the compiler/runtime release you intend to use.
  2. Read the matching release notes and language guide.
  3. Create a .vtr source file.
  4. Run the program with the matching compiler/runtime.
  5. Keep a small test program for each feature you depend on.
  6. Report reproducible errors with the source file and version details.
07 · Roadmap

What a complete language platform needs

  • Formal grammar and versioned language specification.
  • Consistent lexer, parser, semantic analysis and diagnostics.
  • Automated compiler and runtime regression tests.
  • Modules, package management and standard library.
  • Debugger, formatter, language server and editor integration.
  • Stable cross-platform installation and release process.
  • Documented web, database and networking libraries as they become implemented.
